# 01 아키텍처 — 폰 카메라 영상이 PC 화면까지 오는 길

코드를 쓰기 전에 **데이터가 어디서 어떤 모양으로 바뀌며 흘러가는지**를 먼저 잡습니다.
이걸 이해하면 각 함수가 왜 필요한지 저절로 보입니다.

## 1. 전체 그림

```
┌──────────── 스마트폰 (브라우저) ────────────┐        ┌──────────── PC (server.py) ────────────┐
│                                              │        │                                         │
│ 카메라 센서                                  │        │  [스레드 A: aiohttp / asyncio]           │
│   │ getUserMedia (HTTPS 필수)                │        │    GET /     → index.html 파일 응답      │
│   ▼                                          │  HTTPS │    GET /ws   → WebSocket 업그레이드      │
│ <video>  (화면에 미리보기)                   │◄───────│                 ↓ 바이너리 메시지 수신    │
│   │ drawImage                                │        │              FrameQueue.put(bytes)       │
│   ▼                                          │        │                    │                     │
│ <canvas> (RGBA 픽셀 배열)                    │        │                    ▼ queue (스레드 경계) │
│   │ toBlob("image/jpeg", 0.7)                │  WSS   │  [스레드 B: 메인 / OpenCV]               │
│   ▼                                          │───────►│    FrameQueue.get()                      │
│ JPEG bytes (50~150KB)                        │        │    np.frombuffer → cv2.imdecode          │
│   │ ws.send(buf)   ← bufferedAmount 확인     │        │    numpy (H, W, 3) BGR                    │
│   ▼                                          │        │    cv2.imshow                             │
│ WebSocket 소켓                               │        │                                         │
└──────────────────────────────────────────────┘        └─────────────────────────────────────────┘
```

## 2. 구간별 데이터 형태

| 구간 | 데이터 모양 | 크기(720p 기준) |
|---|---|---|
| 카메라 센서 → 브라우저 | 하드웨어 포맷(YUV 등). 우리는 안 건드림 | - |
| `<video>` → `<canvas>` | RGBA 픽셀 배열 (1280×720×4) | 3.7MB |
| `canvas.toBlob(jpeg)` | JPEG 압축 bytes | 50~150KB |
| WebSocket 바이너리 메시지 | 위 bytes 그대로 | 동일 |
| `np.frombuffer` | uint8 1차원 배열 (아직 압축 상태) | 동일 |
| `cv2.imdecode` | numpy (720, 1280, 3) **BGR** | 2.7MB |

핵심: **네트워크를 건너는 순간에만 압축(JPEG)** 하고, 양 끝에서는 픽셀 배열로 다룹니다.
압축 없이 보내면 30fps × 2.7MB = 초당 80MB. Wi-Fi가 못 버팁니다.

## 3. "왜?" 네 가지

### 왜 HTTPS인가
브라우저는 카메라·마이크 접근을 **보안 컨텍스트**(https 또는 localhost)에서만 허용합니다.
폰에서 PC IP로 접속하면 localhost가 아니므로 https가 필수입니다.
공인 인증서는 도메인이 있어야 하니, 실습에서는 자체 서명 인증서를 만들고 폰에서 경고를 무시합니다.
→ `make_cert.py`가 존재하는 이유.

### 왜 WebSocket인가 (HTTP와 뭐가 다른가)
- HTTP: 요청 → 응답 → 끝. 매번 새로 연결. 프레임 30장을 보내려면 요청을 30번 해야 함.
- WebSocket: **한 번 연결하면 양방향 통로가 계속 열려 있음.** 프레임을 그냥 밀어 넣으면 됨.
- 나중에 반대 방향(PC → 폰/드론)으로 "왼쪽으로 가라" 명령을 보낼 때도 같은 통로를 씀.
- wss = WebSocket + TLS. https 페이지에서는 wss만 허용됨.

### 왜 스레드가 2개인가
- aiohttp는 **asyncio 이벤트 루프** 위에서 돎. `await`로 여러 연결을 한 스레드에서 처리.
- `cv2.imshow`/`waitKey`는 **블로킹 함수**이고 GUI 스레드(보통 메인)에서 도는 게 안전.
- 둘을 한 스레드에 섞으면 한쪽이 다른 쪽을 막음. 그래서 스레드 A(네트워크)와 B(화면)로 나누고,
  둘 사이를 **`queue.Queue`** 로 연결. Queue는 스레드 안전(동시에 넣고 빼도 안 깨짐).
- 돔에서 카메라 30대를 받을 때도 똑같이 "수신 스레드들 → 큐 → 처리 스레드" 구조.

### 왜 프레임을 버리는가 (가장 중요)
처리 속도가 수신 속도보다 느리면 프레임이 쌓입니다. 쌓이면 화면은 점점 과거를 보여줍니다.
1분 뒤에는 10초 전 고양이를 보고 드론을 조작하는 사태가 됩니다.
그래서 **두 군데서 버립니다.**
1. 폰 쪽: `ws.bufferedAmount`(아직 전송 못 한 바이트)가 크면 이번 프레임은 건너뜀
2. PC 쪽: `FrameQueue(maxsize=2)`. 큐가 차면 **오래된 것을 빼고** 새 것을 넣음

원칙: *모든 프레임을 처리하는 게 아니라, 항상 최신 프레임을 처리한다.*

## 4. 최종 돔 시스템과의 연결

```
지금:   폰 1대  ──wss──►  PC 서버  ──►  화면
돔:     IP캠 N대 ─rtsp──►  수집 서버 ──► 탐지/추적 ──► ┬─► 사용자 앱 (WebRTC 송출)
        드론 캠  ─────►                               └─► 드론/로봇 제어 (명령 WebSocket)
```
- "폰 브라우저"가 "IP 카메라"로 바뀌고, 프로토콜이 wss에서 rtsp로 바뀔 뿐 서버 쪽 구조는 같음.
- `ws_handler` 자리에 `cv2.VideoCapture(rtsp://...)` 스레드가 N개 들어감.
- `FrameQueue` 뒤에 YOLO(3강)와 추적기(4강)가 붙음.
- 지금 만드는 WebSocket 통로가 나중에 사용자 조작 명령 통로가 됨.
